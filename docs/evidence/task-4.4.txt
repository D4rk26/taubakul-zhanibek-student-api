## Explanation: trigger
- GitHub webhook: GitHub sends an HTTP POST on every push to <jenkins-url>/github-webhook/. Our Jenkins
  listens on 127.0.0.1:8080 (localhost of this laptop), which GitHub's servers cannot reach. In a real
  setup Jenkins has a public HTTPS address (or a tunnel such as ngrok / cloudflared), the webhook is added
  in the repository settings (Payload URL .../github-webhook/, content type JSON, push events) and the
  GitHub plugin starts the scan/build immediately.
- Used instead: polling. For a Multibranch Pipeline the right place is the folder's periodic trigger
  (PeriodicFolderTrigger, interval 2 minutes, from casc.yaml): each scan ("branch indexing") finds new
  branches and new commits and schedules builds. `triggers { pollSCM('H/2 * * * *') }` in the Jenkinsfile
  would only poll an already existing branch job, starts working only after that branch has been built
  once, cannot discover new branches and duplicates the scan — so it is not used.
- Result: commit a92c42d was pushed to main at 23:35:05 without any manual action; the next scan at
  23:36:11 logged "Changes detected: main (c824aef → a92c42d)" and build main #3 started at 23:36:17 with
  the cause "Branch indexing" (not "Started by user") and passed all stages.

## CI vs Continuous Delivery vs Continuous Deployment
- Continuous Integration: every change pushed to the shared repository is built and tested
  automatically, so integration errors are found within minutes.
- Continuous Delivery: in addition, every change that passes CI produces a release-ready artifact that can
  be deployed to production at any time — the deployment itself is a manual decision (button/approval).
- Continuous Deployment: every change that passes all automated checks is deployed to production
  automatically, without a human step.
- This project: CI (checkout, build, test on every push of every branch) plus building and verifying the
  Docker image (a release-ready artifact). There is no deployment stage — it is not required by the task.
